# Agent context coverage by view

Rewritten November 7 from current source: `prototype/agent-adapter.ts`, `runtime/phone-context.ts`, `runtime/device-actions.ts`, `runtime/connection-ui.tsx`, `prototype/mvp-features.ts`, `browser/device-preferences.ts`, and at the pin in `upstream.lock.json` the shared client coordinator (`plugins/plugin-assistant/src/services/device-actions/client-coordinator.ts`), its tool list (`device-actions/tools.ts`), the `VIEWS` action (`packages/agent/src/actions/views.ts`) and `plugin-inbox`. This page describes source. It is not APK, image, live-integration or device acceptance; the evidence column names what was actually run. The Build 49–51 sections at the end are historical. Mock and visual-fixture mode do **not** install the production adapters (`main.tsx`); their simulated agent presentation is not evidence of native integration.

## Shared contract

[agent-adapter.ts](../apps/app/src/prototype/agent-adapter.ts) derives context from `shell.S().view || 'home'` and updates it after component updates. [alpha-client.ts](../apps/app/src/runtime/alpha-client.ts) assigns a revision, cancels an active request and clears proposals when view, selection or sensitivity changes; Back/HOME, disconnect, chooser-open, `document.hidden`, pagehide and the prototype lock/off screens also suspend it. [phone-context.ts](../apps/app/src/runtime/phone-context.ts) sends only an allowlisted view, revision, sensitivity, time zone and an optional bounded opaque selection (`kind`, `id`, `revision` and, where the kind needs them, `accountId`, `sourceRevision`, `occurrenceId`). It rejects sensitive screens and unsupported kinds and never serializes selected text, images, audio, URLs, coordinates, query strings or credentials. An ID alone does not let the model read the object.

Product builds send the user's own text and carry the observation in request metadata (`clientDevice.context`). The text envelope that labels the observation as untrusted client-reported data is a development compatibility path, sent only by `ELIZA_DEV_ALLOW_TEST_MOCKS=1` builds to an unnegotiated peer (`connection-ui.tsx`).

## Action families and where they write

`validateDeviceOperation` (shared coordinator, with Alpha's view list from `device-actions.ts`) admits typed operations bound to owner, agent, device, current context and proposal expiry, with a native journal reservation before the effect and a durable receipt after it. A capability is used only when the connected runtime advertises it and the phone negotiated it at enrollment.

| Family | Operations | Store or effect |
| --- | --- | --- |
| Navigation | `open_view`; the server `VIEWS` action | Renderer view only; no record is read or changed |
| Notes | `create_note`, `notes_query`, `notes_read_selected`, `notes_update`, `notes_delete` (agent tools `DEVICE_NOTE_CREATE`, `DEVICE_NOTES_QUERY`, `DEVICE_NOTE_READ`, `DEVICE_NOTE_UPDATE`) | The phone runs them only on the Previous notes source (`notesStore`). On the agent's Notes, the default, it refuses them and asks the owner to select Previous notes. Agent Notes are the agent's own records, shown through the app-record client and refreshed by a notes effect receipt (`runtime/app-record-completion.ts`) |
| Reminders | `create_reminder` / `reminders.create.v1` and the selected-reminder operations | Native reminder store through `DailyApps`, with receipt recovery |
| Calendar | local event creation, next-event read, selected-event operations, `calendar_named` read and `calendar_availability` (free/busy) foreground reviews | Device calendar provider; both foreground reviews are reviewed on the phone before anything is shared |
| Browser | `browser_navigate` (exact HTTPS URL, no user information); Browser back, forward and reload as view commands | Alpha Browser tab |
| Camera and Photos | `camera_capture_photo`, `photo_library_select` | A new capture or one owner-chosen library item |
| Maps | `maps.selected-read.v1` | Reads the selected place; never starts navigation |
| Clock | `clock.handoff.v1` (Android) | Hands off to Android Clock; the receipt is a dispatch, not alarm state |
| Telephony (verified image only) | `phone.dial.v1`, `sms.send.v1` | System dial screen with the approved number; SMS from the SIM selected in Messages |
| Workflows | `read_selected_notes`, `read_calendar_range`, `post_notification`, `speak_text` | Only inside a reviewed workflow execution |

**What runs without review.** `askBeforeAgentActions` (**Review phone actions first**) defaults to off (`browser/device-preferences.ts`). While it is off, a product build marks the turn `agentActionMode: direct-request-v1`, and `performRequested` in the shared coordinator runs, without a card, up to four proposals bound to that exact user message whose type is `create_note`, `open_view`, `browser_navigate`, `camera_capture_photo` or `photo_library_select`. Workflow proposals and navigation-only cards are excluded. When the toggle is on, or the preference cannot be read, these wait for review, and Browser back, forward and reload are refused. In production, ordinary Notes writes go through the agent's Notes and in-app navigation through the view route below, so the `create_note` and `open_view` entries are seldom reached; neither of those routes reads the toggle. **Every other operation always needs explicit approval**: reminder and calendar writes, every read of a note, event, place or availability, deletes, dial and SMS.

**`VIEWS` and its acknowledgement states.** The server `VIEWS` action lists registered views or shows one exact registered id or label. It does not read or change records. It reports a `view_navigation` effect whose status is `delivered` (the renderer acknowledged the switch), `prepared` (a completed-action handoff: the renderer has bound the navigation and confirms it after the reply), or a failure: `not-delivered`, `forbidden` or `cancelled`. A `prepared` receipt is not proof the screen changed; only the renderer's later confirmation is.

**`open_view` destinations.** `open_view` admits home, reminders and the views `isMvpView` enables: notes, browser, calendar, files, photos, camera, maps, inbox, workflows and settings in every install; phone and messages on the verified Alpha image (`ADMITTED_AOSP_VIEW_ADAPTERS`); contacts on the image only once its adapter is admitted (`admitImageContacts`). Wallet is never admitted in a product build. The `?mode=dev` development profile, available only with `ELIZA_DEV_ALLOW_TEST_MOCKS=1`, admits the deferred views as fixtures; that is not product scope.

**Connections.** Resident, remote and local connections negotiate verified phone actions during enrollment. A Cloud agent connection enrolls the device and gets them when the Cloud runtime advertises the device-action protocol and the owner identity matches; otherwise it stays chat-only and says that phone actions, workflows and paired speech are not enabled. No free-text response is parsed as a command. UI buttons for native app operations are direct owner actions, not model capabilities.

## Historical Build 49 findings versus intentional limits

This section and the ones after it are historical records of earlier builds. Where they differ from the sections above, the sections above describe current source.

Items 1–3 below were identified before the Build 50 source corrections. See corrections and Build 51 evidence below; the historical text is not current unresolved status.

1. **Concrete correctness bug: selected video blocks otherwise valid chat.** `camera-adapter.ts:79` emits `{kind:'video'}`, while `phone-context.ts:5` omits `video`. Opening a native video and sending through remote/Cloud throws “This selected object cannot share agent context.” Add a bounded video identity kind or deliberately map it to an agreed media kind, then test captured-video → chat → selected-ID envelope and leaving/revocation. No source fix was made in this audit.
2. **Missing selected-workflow binding.** A real workflow detail/run is visible, but context remains only `workflows`. A user asking about “this workflow/run” cannot identify it. Add an opaque ID/version plus account/session binding after defining the observation contract; preserve source/output exclusion. This is a missing integration, not evidence that runtime management buttons are fake.
3. **Overlay/background privacy lifecycle needs an explicit contract/test.** Context ignores `s.screen`, chooser-open state and document visibility; agent adapter has no visibility/pagehide listener. Ordinary prototype lock can preserve a previous selection/proposal revision, and opening a credential chooser does not suspend an in-flight request. This does **not** expose screen text under the current identity-only envelope, but does not satisfy a blanket “observation pauses on lock/credential surfaces” claim. Define pause/invalidation for actual native background/lock and credential overlays, then verify stale proposals cannot execute after returning without review. Keep ordinary chat-sheet preservation intentional.
4. **Folder, notification, phone/message and settings-detail context is incomplete.** They emit generic view only; declared allowed kinds do not prove there is an emitter. Missing content/action providers should stay honestly unsupported rather than infer arbitrary strings as authority.
5. **Cloud phone actions (historical Build 49 finding, since changed).** At Build 49 the Cloud active type had no `DeviceActions`. Current source enrolls the device with a Cloud agent and negotiates verified phone actions when the Cloud runtime advertises the device-action protocol; a runtime without it stays chat-only. Live Cloud device-action acceptance remains open.
6. **All fourteen views have a generic context route, not fourteen live integration passes.** Live local evidence explicitly covers Notes/context and the bounded action slice. Maps has a targeted renderer observation test; inbox has lifecycle fixtures. No existing single test proves all native-selected kinds, overlays, account changes and real model replies end-to-end.

## Minimum next verification

After coordinated source fixes, use one authenticated local session and repeat against actual Cloud/enclave when authorized: navigate each row, open a real fixture selection, send a harmless “identify my current view and opaque selected ID; do not perform actions” request, compare the transmitted bounded envelope and model response, then change selection/view/account and verify cancellation/stale-approval refusal. Add positive/negative coverage for video, workflow/version, folder selection, sensitive wallet/secure lock and credential-overlay/background transitions. Explicitly verify no body/URL/coordinates/credential fields appear in observation metadata or envelope. Preserve separate user-approved content-sharing and effect tests; do not add autonomous side effects to this context audit.

## Build 50 source corrections (not APK acceptance)

The findings above describe the pre-fix Build 49 source audit. The next candidate now includes `video` in `phone-context.ts`'s bounded identity allowlist. No image/video bytes, content URI, caption, filename, or other arbitrary media fields are retained. The camera adapter's existing real provider selection is unchanged. The remote transport (`remote-protocol.ts:224`) sends metadata without a second selected-kind enum; upstream `packages/agent/src/api/chat-routes.ts:2174` reads object metadata and enriches declared UI view fields, without rejecting `video`. `conversation-routes.ts` passes this to generation. The legacy development gateway ([dev-agent.mjs](https://github.com/eliza-research/alphaphone/blob/f3b1db5cf17250472407fa2b125c48ac94dbb969/scripts/dev-agent.mjs#L231)) checks bounded identifier syntax rather than a selected-kind enum. The existing model-visible observation envelope also carries this identity for Cloud shared hosts that ignore metadata. No upstream schema patch is needed for video.

`agent-adapter.ts` now reads the workflow adapter's authenticated, session-bound `workflowSelection()` getter. Only workflow ID and version are included, not code, run output or credentials. Chooser-open, `document.hidden`, pagehide, and verified prototype `screen === 'lock'/'off'` states now suspend context. This increments the existing context revision, cancels pending client turns and clears proposals while preserving the connected transport and conversation history. Closing/foregrounding permits a new explicit turn; stale responses are discarded. Document visibility and prototype screen state do not establish native Android Keyguard state. Cancellation remains best effort for already dispatched server work or committed native effects.

`node scripts/test-agent-context-browser.mjs` passes against a **fresh dedicated local Vite process** with actual production renderer/adapters and synthetic AlphaPhotos/agent boundaries. It opens the video tile and Ask Alpha sheet, sends through the actual composer, verifies only opaque video ID/revision reach the observation, then exercises chooser, visibility, and pagehide cancellation. It verifies blocked sends while suspended, expired proposals, stale reply suppression, retained prior messages/session and successful fresh requests. Seven outbound synthetic requests are expected; no native capture, model call or Cloud acceptance is claimed. `npm run typecheck` passes. Real native per-view tests and APK verification remain separate. Do not reuse an HMR-modified Vite process: timestamped imports can create a second controller instance in a test's dynamic imports.
