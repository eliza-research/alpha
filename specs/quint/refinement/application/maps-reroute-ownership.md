# Mounted Maps reroute ownership

The replay opens and starts Maps through the production renderer in Chromium.
The registered resident Maps port begins an agent reroute after a precise
synthetic fix. Its synthetic provider holds the reply and can resolve or
refuse after its signal aborts. The replay drives End, origin input, Start and
duplicate touch through real controls. The browser blocks external requests
and uses a local style, a closed account transport and synthetic location.

The original mounted behavior returned success from the replacement
guidance when the retired request settled after another Start. Both late
success and late refusal produced this outcome. A live reroute that
published a new origin with the original provider route ID returned
`MAPS_DEVICE_UNAVAILABLE`. The screen kept the correct route in all three
cases. A reply that arrived before the replacement Start already refused.

A route planning receipt identifies the exact admitted ready or error
publication by its controller revision. The screen matches that revision
to its own guidance session. The agent checks the live guidance session
before reporting success and reports a provider refusal only from its
matched receipt. An accepted route can keep its original public ID. End
still allows the route request to finish for review when it has no
replacement, while the ended guidance stays retired.

The source replay checks one mounted component, one agent reroute, two
guidance starts, three route requests and selected settlement orders.
Each settlement checkpoint includes completion of the agent reply.
Android task removal is a separate boundary. The native service receives
the removed root component and compares it with the current foreground
owner. The controlled callback cannot distinguish old and new Android
tasks with the same root component. Installed task attribution, physical
location, real Cloud delivery and unrestricted scheduling remain open.
